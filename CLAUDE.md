# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Chrome MV3 sidebar extension for DealNews editorial use. It has two purposes:
1. **Card generator** — look up offers in DatoCMS and generate styled HTML deal cards for longform articles
2. **Article scanner** — read an article's HTML from the CMS editor, identify deal cards, check expiration status via DatoCMS, remove flagged cards, and regenerate clean HTML for the editor to copy/paste back in

The extension is loaded unpacked at `chrome://extensions`. There is no build step, bundler, package.json, test suite, or linter — all files are vanilla JS/HTML/CSS loaded directly by Chrome, and verification is manual (reload the extension, exercise the tab in the sidebar).

This repo also holds `index.html`, a standalone Live Feed generator tool unrelated to the extension's own load path — see "Live Feed Generator" below.

## Reloading after changes

After editing any file, go to `chrome://extensions`, find "DealNews Blog Card Editor", and click the reload (↻) icon. Then close and reopen the sidebar.

## Versioning

Bump `"version"` in `manifest.json` (semver) whenever a change lands that alters what the extension *does* — new functions, changed behavior, bug fixes. Purely cosmetic edits (comments, formatting, this file) don't need a bump.

- Patch (`x.x.PATCH`) — bug fixes, small behavior corrections
- Minor (`x.MINOR.x`) — new functionality, non-breaking additions
- Major (`MAJOR.x.x`) — significant overhauls or breaking changes to how a tab/flow works

## Architecture

```
manifest.json       MV3 manifest — declares permissions, content script, side panel
background.js       Service worker — opens side panel on toolbar icon click
content.js          Injected into secure.dealnews.com — handles editor detection and read/write
sidebar.html        3-tab UI + daily counter strip — no inline event handlers (blocked by MV3 CSP)
sidebar.css         All styles — dark mode via [data-theme="dark"] CSS variables
sidebar.js          All sidebar logic — DatoCMS API calls, card generation, article flow
icons/
  generate-icons.html   Open in browser to regenerate PNG icons
index.html          Live Feed Generator — standalone, not part of the extension, see below
```

### Tabs (`sidebar.html` / `sidebar.js`)

- **Configure** — add offers by DatoCMS or legacy ID, reorder/sort/lock them, edit CTA text (`addOfferById`, `sortOffers`, `moveOffer`); has its own Edit/Preview/HTML sub-nav — see "Configure sub-tabs" below
- **Processor** — standalone bulk find/replace utility: pastes arbitrary HTML and rewrites the text of every element carrying the `PROC_TARGET_CLASS` class token (`btn-cta`); unrelated to the offers list state (`processHTML`)
- **Article** — the article scanner flow described above (`loadFromPage`, `checkAllExpirations`, `removeAndRegenerate`); also has an optional visual preview of loaded cards (`toggleArticlePreview`/`renderArticlePreview`, see "Article visual preview" below), an automatic data-iref tag audit with a per-card and bulk in-place fix (`analyzeIrefTags`/`applyIrefFix`/`fixAllIrefIssues`, see "Iref tag audit" and "Iref fix" below), an optional per-card/bulk move into an article's existing Expired-cards grouping instead of removal (`toggleMoveToExpiredGroup`/`moveAllExpiredToGroup`, see "Expired group" below), and a plain-text Find & Replace against the loaded HTML with a preview-then-apply match list (`previewArticleFindMatches`/`applySelectedFindReplacements`, see "Find & Replace" below)

There was previously a 4th "Live Feed" tab; it was removed in `2.20.1` and now lives only in the standalone `index.html` — see "Live Feed Generator" below.

### Configure sub-tabs

The Configure tab holds three views — Edit, Preview, HTML — behind an internal `.subtabs` nav (`setSubTab()`), not three separate top-level tabs. They used to be separate tabs; merged because all three already operated on the same `offers` array and already cross-linked (Preview's "View HTML →" button, still present, now calls `setSubTab('html')` instead of the old `setTab('html')`).

`setSubTab()` mirrors `setTab()`'s pattern exactly (toggle `.subpane`/`.subtab` `active` classes by name) but is a separate function/array (`['edit', 'preview', 'html']`) — `setTab()` itself now only knows about the four real top-level tabs (`configure`, `processor`, `article`, `live`) and has no awareness that Configure has sub-views at all. Don't merge these two functions or arrays; a sub-view name colliding with a future top-level tab name (or vice versa) would silently break the wrong one.

Re-rendering behavior is unchanged from when these were top-level tabs: `renderPreview()`/`renderHTMLOut()` run only on switching *into* that sub-view (inside `setSubTab()`), not live on every offers edit — except `setCardLayout()` (the Grid/Vertical toggle), which still eagerly re-renders both regardless of which sub-view is currently visible, exactly as it did before the merge.

`.subtab`/`.subtabs` (sidebar.css) are visually similar to `.sort-btn` (same pill shape, same active-fills-dark treatment) but are a deliberately separate class — `.sort-btn` means "sort/layout mode," `.subtab` means "which view is showing." Don't collapse them into one class; they're reused independently and a shared class would make a future style change to one silently affect the other.

### Daily counter

A strip between the token bar and the tabs (`.daily-counter`, visible from every tab) shows "Today: Deals N · Picks N" for one author, chosen once via ⚙ (`#count-author`, populated from the Author model `2041376`, persisted as `countAuthorId`). It exists so the editor doesn't have to keep reloading saved searches in the separate **DealNews Offer Creator** extension (a teammate's extension, where deals and creator picks are actually written) to check daily progress. Chrome doesn't let one extension script another extension's pages, so the counts come from DatoCMS directly, replicating that extension's Offer Manager queries:

- **Deals** (`fetchDealsTodayCount()`) — CMA `/items?filter[type]=offer` with `author` = the chosen author, `_first_published_at` ≥ ET midnight, and `curation_level` not in `bulk`/`verified_bulk` (the Offer Manager's default exclusion of automated offers); `page[limit]=1` and read `meta.total_count`, so it's one cheap request.
- **Picks** (`fetchPicksTodayCount()`) — GraphQL CDA (`graphql.datocms.com`, `X-Environment: main`) `_allOffersMeta` count with `curatorsPick: { any: { curatorsPick: { author: { eq } } } }` plus the same date/curation filters. Filtering on a block's author is only exposed by the CDA, not the CMA's `/items` filters. Note the date is the *offer's* publish date, not when the pick was added — a pick added today to an older offer isn't counted. That matches the Offer Manager's own "Today" filter on picks.

"Today" is ET midnight (`etMidnightTodayISO()`, same noon-probe DST technique as the Offer Manager's `etDateToUTC()`). The two requests are independent (`Promise.allSettled`), so a token without CDA access still shows the deals count, with "!" and the error as a tooltip on picks. Refreshes on load, every 5 minutes (`COUNT_REFRESH_MS`) while the panel is visible, on becoming visible again, on a token change, and via ↻. If the Offer Manager's filter logic changes, these queries need to change with it — its source is in the installed extension (ID `ejlmoeacegilkkgjlbcfbfmfalpneidh`), `src/pages/offer-manager.js` `buildFeedUrl()` and `src/pages/offer-manager-picks.js` `buildCdaOfferFilter()`.

### Change Log

A collapsible "Change Log" panel sits below the tabs (visible from every tab, not tab-specific) and records what the Processor and Article tabs actually did each time they run — `logChange(source, summary, details)` in `sidebar.js`. It's the diagnostic trail for tracking down why generated/regenerated HTML doesn't match expectations, so log real specifics (card titles, offer IDs, before/after text, position numbers), not vague summaries.

- `processHTML()` logs the count of retexted buttons plus each one's before → after text.
- `removeAndRegenerate()` logs which cards were removed (with title, offer ID, and why — flagged/expired/deleted), which cards moved and from/to which position, whether any `<head>`-parsed content (e.g. JSON-LD `<script>` blocks, see "Generated HTML" below) was carried through, and logs the no-op case too ("nothing to do") rather than silently doing nothing.
- Entries are session-only (`changeLog` array, capped at `CHANGE_LOG_MAX` = 50) — not persisted to `chrome.storage`, same as `offers`/`articleCards`. Every entry is also mirrored to `console.log` for copying full detail out of DevTools.
- The Configure tab's card generation (`generateHTML`) is deliberately NOT logged here — there's no "before" HTML to diff against, just a fresh list of offers, so a log entry would just restate the Configure tab's own state.

### Tracking link detection

`findTrackingLinkMatches(html)` (`TRACKING_LINK_PATTERN` regex) flags two DealNews tracking-link shapes wherever raw HTML enters the tool: `dealnews.com/lw/artclick.html`-style links (matched on the bare `artclick` keyword) and `/lw/click.html`-style links (matched on the fuller `/lw/click.html` path, not a bare `click` keyword — unlike `artclick`, "click" alone is common enough in unrelated URL/attribute text, e.g. `onclick`, that matching it bare would false-positive far more than the distinctive `artclick` token does). Both shapes are flagged together into one combined count/list rather than tracked as separate checks — either one found anywhere means the same thing to the user: a tracking link snuck into HTML about to be copied out. It scans the raw HTML *string*, not parsed DOM/attributes — the pattern can appear in plain body text as well as link attributes, so string matching catches both without needing to enumerate every attribute that might carry a URL.

Three independent call sites, each rendering its own banner via `renderTrackingLinkBanner(prefix, matches)` (`${prefix}-tracking-banner` element) and logging a Change Log entry when matches are found:
- `parseAndDisplayCards()` → `article-tracking-banner` — checked on whatever HTML was loaded (Load from Page or Paste manually both funnel through this function), *before* card parsing, so it still runs even if no `.bu-card` elements are found.
- `removeAndRegenerate()` → `regen-tracking-banner` — re-checks the actual regenerated output, independently of the load-time check. A card removal can eliminate the article's only tracking link (banner clears) or leave one behind in surrounding body text that isn't part of any card (banner stays lit even though the flagged card is gone) — don't assume the load-time and regen-time results will match.
- `processHTML()` → `proc-tracking-banner` — checked against the Processor tab's raw pasted input.

Each banner is independent state tied to its own HTML snapshot; there's no single "does this article have a tracking link" flag, because the article's own HTML, the tool's regenerated output, and whatever's pasted into the Processor tab are three different strings that can disagree.

### Update check

`checkForUpdate()` compares `chrome.runtime.getManifest().version` with the `version` in `main`'s `manifest.json` (`UPDATE_MANIFEST_URL`, raw.githubusercontent.com, which sends `Access-Control-Allow-Origin: *` so no host permission is needed) and shows `#update-banner` only when the remote is strictly newer. The result is cached 6 hours in `chrome.storage.local` (`updateCheck: {checkedAt, latest}`, recorded even on a failed fetch so it isn't retried on every open); dismissing stores `updateDismissed` = that version, so the banner stays hidden until a still-newer version appears. The remote file is treated as untrusted — the version is only accepted if it matches `^\d+\.\d+\.\d+$` and is written with `textContent`, never `innerHTML`. A failed fetch (offline, repo made private again) just means no banner. **The banner only fires for versions merged to `main`** — work sitting on a feature branch or unpushed is invisible to it, so a release isn't "live" for other users until it's merged. It tells users to `git pull` in the extension folder and reload at `chrome://extensions`; it can't update anything itself.

### Blog Content ID auto-detect

The CMS article edit page's URL carries the article ID (`https://secure.dealnews.com/admin/phews/features/article/?article_id=2218015`), which is exactly the Blog Content ID `data-iref` needs. `applyDetectedBlogId()` reads it from the active tab's URL (the sidebar already has the `tabs` permission, so no content-script change) via `articleIdFromUrl()`, which only trusts the `article_id` param on the `secure.dealnews.com` host and only when it's all digits — a wrong auto-fill would silently mis-tag every card, which is worse than leaving the field blank. It runs on panel open, on tab switch/navigation (`chrome.tabs.onActivated`/`onUpdated`), and at the start of "Load from Page". Rules: a *different* article than last time always replaces the field (the old value belonged to the previous article); the *same* article respects a manual edit (`blogIdEditedByUser`) instead of overwriting it; a non-article tab changes nothing, so a value typed by hand stays. `#blog-id-source` labels the value "✓ from page URL" or "entered manually". If the CMS ever changes its URL shape, `articleIdFromUrl()` is the one place to update.

### Message passing

The sidebar cannot access the page DOM directly. `sidebar.js` sends messages to `content.js` via `chrome.tabs.sendMessage`, and `content.js` responds:

- `GET_ARTICLE_HTML` → returns `{ html, source, editorId }` — reads article body from detected editor
- `GET_DIAGNOSTICS` → returns editor environment info for debugging (run on demand via the "Run Diagnostics" button only — not on every `GET_ARTICLE_HTML` call, to avoid extra UI scroll)

Both messages accept an optional `selector` field (from `#editor-selector` input, persisted to `chrome.storage.sync`) to override auto-detection.

`content.js` also defines `SET_ARTICLE_HTML`/`setEditorHTML()`, but nothing in `sidebar.js` currently sends that message — see "No Save to Page" below.

### Editor detection (`content.js`)

`detectEditor()` tries in order: user CSS selector override → TinyMCE → CKEditor 4 → textarea containing deal card HTML → largest textarea by content length → contenteditable. CodeMirror is detected via `el.CodeMirror` on the textarea element, not `window.CodeMirror`.

**Do not read article HTML from the live rich-text iframe instead of the textarea mirror** — this was tried (to fix a suspected stale-mirror read issue) and broke card parsing entirely. The iframe's `designMode` document sanitizes/normalizes content as soon as it's loaded, stripping the custom classes (`.bu-card`, `.bu-columns`, etc.) that `parseAndDisplayCards()` depends on. The textarea's raw `.value` is the only reliable read source, despite being a periodically-synced mirror.

### No "Save to Page" — copy/paste only

A "Save to Page" button once wrote the regenerated HTML directly into the editor via `chrome.scripting.executeScript` (`world: 'MAIN'`). It was removed because the article body field on secure.dealnews.com is a legacy WYSIWYG rich-text iframe (see below) whose own internal content-sync logic can't handle the nested `.bu-card` markup this tool generates — writing into the iframe's `body.innerHTML` renders fine, but the editor's own sync-back-to-textarea routine flattens the DOM to plain text (even leaking hidden `<script>`/`<style>` text as visible prose), destroying structure and styling. Writing straight to the underlying textarea doesn't work either — the iframe periodically re-syncs and clobbers it. The Article tab's "Copy" button is the reliable path: it copies the regenerated HTML (with structured data and inline styles intact, see below) for the editor to paste in manually.

### MV3 CSP constraint

**No inline `onclick=""` attributes anywhere in sidebar.html** — they are silently blocked. All event listeners are wired in the `DOMContentLoaded` handler in `sidebar.js`. Offers table (`#offers-tbody`) and article card list (`#article-card-list`) use event delegation for dynamically rendered rows.

### Storage

- API token: `chrome.storage.sync` key `datoToken`
- Theme preference: `chrome.storage.sync` key `theme`
- Editor selector override: `chrome.storage.sync` key `editorSelector`
- Daily counter author: `chrome.storage.sync` key `countAuthorId` (a DatoCMS Author record ID)
- Update-check cache/dismissal: `chrome.storage.local` keys `updateCheck` and `updateDismissed` (per-machine, deliberately not synced)
- None of these use `localStorage`

### DatoCMS API

Base URL: `https://site-api.datocms.com`. Offer expiration is checked against the `expiration_datetime` field (configurable via `#exp-field` in the Article tab settings — this API key is specific to the DealNews offer model and isn't discoverable from schema access alone). Legacy numeric IDs are resolved to Dato IDs before fetching item details.

If the configured expiry field name is wrong, `fetchOfferStatus()` doesn't error — it silently treats every offer as active unless DatoCMS `meta.status` is non-`published` or the record 404s. To make a misconfigured field name discoverable without DatoCMS schema access, `fetchOfferStatus()` distinguishes "field key not present in the response at all" from "field present but empty," and in the former case returns a reason listing every real attribute key on that record; `checkAllExpirations()` stores this on `card.reason` and it's surfaced as the status badge's tooltip.

### Offer description formatting (dast → HTML)

`getValueStatement()` reads the offer's modular content field, which stores rich text as DatoCMS structured text (dast) — a JSON node tree, not HTML. `dastNodeToHTML()` converts that tree into real HTML (`dastNodeToHTML`, replacing a prior `extractDastText()` that only concatenated leaf `span` text and silently dropped every list, link, and inline style). Only leaf `span` text goes through `esc()`; the tags this function itself emits (`<p>`, `<ul>`/`<ol>`/`<li>`, `<a>`, and the `DAST_MARK_TAGS` inline styles) are trusted structure, not user data, so they aren't escaped a second time — `generateHTML()` and the Configure tab's Preview (`renderPreview()`) both insert `o.valueStatement` directly for this reason. Don't wrap it in `esc()` again at either call site; that would turn the real tags into visible `&lt;ul&gt;`-style text instead of rendering them.

`itemLink` (a dast link to another DatoCMS record, distinct from a plain `link` node with its own `url`) renders as plain text, not a real `<a>` — resolving its target would need an extra fetch per link, and offer copy overwhelmingly uses plain external links rather than internal record references, so it wasn't worth the added requests for what's expected to be a rare case.

Because the description can now legitimately contain block-level content (a `<ul>`, multiple `<p>`s), `generateHTML()` wraps it in a `<div class="bu-content bu-is-flex-grow-1">`, not the `<p class="bu-content bu-is-flex-grow-1">` it used before — a `<ul>` inside a real `<p>` is invalid HTML and browsers silently close the `<p>` early, breaking the layout. `parseAndDisplayCards()`/`refreshArticleCardFields()` (Article tab) look this element up by class token (`.bu-content.bu-is-flex-grow-1`) rather than tag name specifically so they keep matching both old (`<p>`) and new (`<div>`) cards — the same reasoning as `PROC_TARGET_CLASS`'s token match. The `.bu-is-flex-grow-1` qualifier matters because the CTA button's own wrapper div also carries a plain `.bu-content` class; without it, a generic `.bu-content` selector would still happen to resolve correctly today only because the description div comes first in DOM order — don't rely on that ordering elsewhere.

### Generated HTML

`generateHTML()` has two render-time toggles on top of Grid/Vertical (all session-only, none touch `offers`): `showImages` (false omits the image column entirely, leaving a single full-width text column) and `cardStyle` ('standard' | 'compact', experimental). Compact output differs from standard in: no separate callout line (the callout is a `.content-call-out` span *inside* the headline link: spliced before the "Promo Code"/"Coupon" phrase for discount callouts on promo headlines, otherwise suffixed with "for" after a plain price or an en dash); `<h3>` loses `bu-is-4` and carries inline `font-size: 24px; font-weight: 400; line-height: 32px`; the CTA wrapper sits right after the headline (with `bu-mb-4` instead of `bu-mb-0`) and the description follows it. The Preview sub-view mirrors the structure but uses a smaller headline (`.card-h3-compact`) to fit the sidebar — layout fidelity only, not size fidelity. When reading cards back (`parseAndDisplayCards()`/`refreshArticleCardFields()`), use `findCardLinks()`/`cardTitleText()`/`cardCalloutText()` rather than `querySelector('a')`/raw `h3.textContent` so both styles and image-less cards parse correctly.

Each `.bu-card` element gets a `data-offer-id` attribute set to the DatoCMS item ID. The Article scanner uses this attribute to extract IDs when checking expiration — articles generated before this attribute was added will show "Unknown" status.

The Configure tab's Grid/Vertical buttons (`setCardLayout()`) control the `#custom-offers-list` container class in `generateHTML()`: Grid (default) uses `bu-columns bu-is-multiline bu-is-3` for a multi-column layout on the live site; Vertical uses a plain `bu-vertical-offers` class with no Bulma grid classes, so each full-width `.bu-card` just stacks in normal block flow. Only the outer container changes — each card's own internal layout (image left, text right via its own nested `.bu-columns`) is the same in both modes. `cardLayout` is session-only state, same as `offers` — it resets to `'grid'` on reload rather than persisting to `chrome.storage`.

The CTA `<a class="btn btn-cta bu-m-0">` is sized to fit its own text, not stretched to fill its column — it used to also carry `bu-is-flex-grow-1` (a Bulma-style `flex-grow: 1` utility from DealNews's site framework), which made it stretch to the parent flex container's full width regardless of CTA text length. That class was dropped so button width tracks the CTA text. The Configure tab's Preview sub-view (`.card-cta`, sidebar.css) mirrors this — no `flex: 1`.

Each of a card's three links (image, title, CTA button) gets its own `data-iref` click-tracking attribute: `site-widget-card-blog-{blog content ID}-{offer legacy ID}-{image|title|button}`. `buildDataIref(blogContentId, legacyId, linkType)` builds this string and deliberately returns `''` (attribute omitted entirely) when `#blog-content-id` (Edit sub-view) is blank — a half-formed tracking string would silently corrupt reporting data, which is worse than the attribute simply being absent. `renderHTMLOut()` shows a warning banner in the HTML sub-view whenever it's blank, right next to the Copy button, so the gap is visible at the moment it matters rather than only in the Edit view where the field lives. `fetchOffer()` now also reads `attrs.legacy_id` off the offer record itself (defaulting to `'0'` if absent, matching this codebase's existing "0 = no value" convention for vendor/category/brand) — this is the *offer's own* legacy ID, unrelated to the vendor's legacy ID (`vendorLegacyId`) already resolved a few lines below it; don't conflate the two. `#blog-content-id` is session-only state (not persisted to `chrome.storage`) since it's specific to whichever article is currently being worked on, not a durable preference; it's normally auto-filled from the CMS page URL (see "Blog Content ID auto-detect" above) and only needs typing by hand off the CMS or when the URL shape isn't recognized. This only applies to `generateHTML()`'s real output — the Preview sub-view's mockup (`renderPreview()`) never gets these attributes, since nothing in it is ever actually published.

This attribute was named/built as `iref-append` through `2.23.x` — the wrong attribute name entirely, confirmed against DealNews's live site: `iref-append` belongs to the unrelated `blog-slider` carousel widget (see "Blog Slider (removed)" below) and had no effect on these cards, nor did it survive the publish transform into rendered HTML. `data-iref` is read by a separate, already-global mechanism (`DN.handleClickURLs`/`DN.iref` in DealNews's shared site JS — a delegated `mousedown` listener on `document.body` that appends `iref=<value>` onto a clicked same-origin anchor's outbound URL whenever that anchor has a non-empty `data-iref`), so no widget-side changes were needed, only the attribute name. The value format itself was already correct and unchanged. Whether DealNews's publish-time HTML transform strips `data-iref` the way it currently strips `iref-append`/`vendor`/`brand`/`category`/`landing_url` is outside this extension's control — that pipeline lives on DealNews's side, not in this repo, and needs its own allowlist update (alongside `title`, which already survives) for this fix to take effect on the live site.

`PROC_TARGET_CLASS` (`'btn-cta'`) is matched as a CSS class selector (`.btn-cta`), not an exact full-class-string comparison — pasted HTML in the Processor tab may be from an older card generation (with `bu-is-flex-grow-1`) or the current one (without it), and token matching finds the button either way. Don't revert this to an exact `class` attribute equality check; it would silently stop matching one generation or the other.

`removeAndRegenerate()` in `sidebar.js` parses the original article HTML with `DOMParser` and removes flagged/expired `.bu-card` elements. It concatenates `doc.head.innerHTML + doc.body.innerHTML` (not just `doc.body.innerHTML`) — leading `<script>`/`<style>` blocks (e.g. JSON-LD structured data) get parsed into the synthetic `<head>` by `DOMParser` since they're "metadata content" appearing before any real body element forces the parser out of "in head" mode. Dropping `doc.head` would silently lose that content.

Both `parseAndDisplayCards()` and `removeAndRegenerate()` locate cards via the shared `findCardElements(doc)` helper (`doc.querySelectorAll('#custom-offers-list .bu-card')`, falling back to `.bu-card` if that's empty). Browsers don't enforce id uniqueness for CSS selector matching, so this matches cards inside *every* element with `id="custom-offers-list"`, not just the first — this matters when an article's cards have been split across more than one such container (e.g. an editor separated the deal list into two groups). `card.index` is this combined list's position, so both functions must use the exact same lookup or a card's index will point at the wrong element (or nothing) in the other function. A prior version of `removeAndRegenerate()` used `doc.querySelector('#custom-offers-list')` (first match only) instead of this shared helper, which silently broke removal for any card in a second/later container — don't reintroduce a second, divergent card-lookup implementation.

Flagging for removal: cards can be flagged individually (🚩 per card), all at once (`setAllFlags(true)`/"Flag All for Removal"), all cleared (`setAllFlags(false)`/"Unflag All"), just the ones that failed the expiration check (`flagExpired()`/"Flag Expired" — flags `status === 'expired' || 'deleted'` only, leaving active/unchecked cards alone), or everything *except* the intentionally-kept ones (`flagAllExceptKept()`/"Flag All Except Kept" — flags every card regardless of status, skipping only `keepDespiteExpired` cards). The latter two both skip `keepDespiteExpired` cards but differ in what they flag otherwise: `flagExpired()` is scoped to confirmed-expired cards, `flagAllExceptKept()` is everything-but-Keep — useful when an editor wants to clear an article down to just its intentionally-kept cards without individually unflagging each Keep card first. Removal isn't the only fate for an expired card, though — `card.moveToExpiredGroup` (mutually exclusive with `card.flagged`) marks it to be relocated into the article's existing Expired-cards section instead of deleted; see "Expired group" below.

`card.flagged` is the *only* thing `removeAndRegenerate()` checks to decide what to remove — `toRemove` is built from `c.flagged` alone, not from `c.status` directly. A prior version of `toRemove` also matched on `c.status === 'expired' || 'deleted'` independently of flagging (fixed in `2.25.1`), which meant Regenerate silently removed *every* card the live DatoCMS check found expired/deleted, whether or not the user had actually flagged it — catching unflagged cards the user had no intention of touching yet, `keepDespiteExpired` ("Keep") cards (nothing exempted them), and `moveToExpiredGroup` cards (expired status is exactly why a card gets marked for that move, so it was being deleted outright instead of relocated — `toMoveToExpired`'s `!toRemove.has()` guard excluded it once it was already caught by the status check). Don't reintroduce a status-based check here; every path that should turn "expired" into "removed" (`flagExpired()`, `flagAllExceptKept()`) already does so by setting `card.flagged = true`, so `toRemove` only ever needs to read that one field.

### Intentionally-expired cards ("Keep")

Some cards are expired on purpose — the CTA button text itself says "Expired" (or similar) as an editorial choice to leave the card visible rather than remove it. `parseAndDisplayCards()` detects this at parse time by reading the CTA element's text (via the same `.${PROC_TARGET_CLASS}` selector used elsewhere) and testing it against `EXPIRED_CTA_PATTERN` (`/expired/i`), storing the result on `card.keepDespiteExpired` — independent of and prior to any live DatoCMS status check, since the CTA text is the actual source of truth for "an editor already decided this stays."

`flagExpired()` ("Flag Expired") skips any card with `keepDespiteExpired` set, so the automatic expired-card sweep won't catch these — but per-card 🚩 flagging and "Flag All for Removal" still work on them normally, since those are explicit overrides rather than an automatic scan. The card list shows a distinct blue "Keep (CTA: Expired)" badge (`badge-keep`) for these, taking priority over the DatoCMS-status badge (but not over "Flagged," if explicitly flagged) — see `badgeClassForStatus()`/`badgeLabelForStatus()`/`badgeTitleForCard()`.

### Article visual preview

`toggleArticlePreview()` shows/hides a `renderArticlePreview()` grid below the found-cards list, mimicking the Configure tab's own Preview (`renderPreview`) but sourced from `articleCards` instead of `offers`. Purpose: a live DatoCMS status check can't say anything about a card with no `data-offer-id` (see "Generated HTML" above — older cards predate that attribute), and even a checked/active card can carry stale text a human would recognize instantly ("Ends 2025", "Expired", a dead promo code) that the status field doesn't capture. Reusing `.card-wrap`/`.card-preview`/etc. (sidebar.css) means this needed no new card-rendering CSS.

`parseAndDisplayCards()` extracts the extra fields this needs — `imageUrl`, `callout`, `valueStatement` — using the same selectors `generateHTML()` writes (`.content-call-out`, `p.bu-content`) but with fallbacks (`.price`, plain `p`) for older card markup that predates those exact classes; a missing field just renders blank rather than breaking the parse. Each card shows a "⚠ Unverifiable" badge when `!card.offerId`, calling out exactly the cards a DatoCMS check can't vouch for, alongside the normal status/keep/flagged badge from `badgeClassForStatus()`/`badgeLabelForStatus()`/`badgeTitleForCard()`.

`renderArticleCards()` calls `renderArticlePreview()` itself whenever `articlePreviewVisible` is true, so every caller (parse, reorder, drag) keeps the preview in sync for free instead of needing to remember to refresh it separately.

Each preview card also has its own flag/unflag button (`[data-action="toggle-flag"]`, delegated on `#article-preview-container`), so a card spotted as stale while eyeballing the preview can be flagged right there instead of scrolling back up to the list. It calls the same `toggleFlag(index)` the list's 🚩 button uses — not a separate code path — so list badge, status bar, and preview all reflect one flag state. `toggleFlag()` re-renders the whole preview (rather than patching just that button, the way it patches the list row in place) since the preview button's label text and the card-wrap's dimmed/outlined "flagged" look (`.card-wrap.flagged`, sidebar.css) both need to change together.

### Iref tag audit (Article tab)

`analyzeIrefTags(imageLinkEl, titleLinkEl, ctaLinkEl)` is the Article tab's read-only counterpart to `buildDataIref()` (see "Generated HTML" above) — instead of writing the `data-iref` tracking attribute, it checks whether a card already loaded from an article actually has it, on each of the same three links (image, title, CTA button). A link with no `data-iref` attribute at all, and a title/button link whose element wasn't found in the first place (e.g. no CTA matched), are treated identically — both mean that link has zero tracking, so there's no reason to distinguish them in the result. The exception is the *image* link: a card with no image link at all (generated with the Images toggle off) is N/A, not missing — see `findCardLinks()`. It also flags a present attribute whose own linkType suffix doesn't match the link it's actually on (e.g. `-image` sitting on the title link) — a mismatch a bare presence check would miss, most plausibly caused by manual HTML editing or an errant find/replace.

This only checks presence/shape, not correctness against a specific blog content ID or offer legacy ID — the Article tab has neither of those on hand by default (`#blog-content-id` is Configure-tab state, and resolving an offer's `legacy_id` means an extra DatoCMS fetch per card). Presence and linkType-suffix agreement are both free, purely-local DOM checks, which is also why this runs automatically on every parse rather than sitting behind its own button — same reasoning as the "⚠ Unverifiable" badge below. The fix action below (`applyIrefFix()`) is the one place that *does* spend the extra fetch, since only then is the resolved legacy ID actually needed.

`parseAndDisplayCards()` and `refreshArticleCardFields()` both call it (storing `card.irefMissing`/`card.irefMismatched`, each an array of `'image'|'title'|'button'`) so the audit stays current after a find/replace edit, not just after a fresh load. `irefBadgeHTML(card)` renders a "🔗⚠ iref issue" badge in the visual preview only — same placement as "⚠ Unverifiable" — when either array is non-empty; a clean card gets no badge at all. `updateArticleStatusBar()` also tallies `N with data-iref issues` so the count is visible without opening the preview. A card that only carries the old, pre-2.23.2 `iref-append` attribute (see "Generated HTML" above) shows up as missing here too — it genuinely has no working tracking, and needs the fix below (or a fresh regenerate) either way.

### Iref fix (Article tab)

`applyIrefFix(i)` writes the actual `data-iref` attribute(s) onto an already-loaded card's links, so a card flagged by the audit above can be repaired in place instead of needing to be regenerated fresh from the Configure tab. It's wired to a "🔗 Fix iref" button (`irefFixButtonHTML()`) that only renders next to the "🔗⚠ iref issue" badge in the visual preview — a clean card has no button, same as it has no badge. While writing `data-iref` onto a link, it also strips any leftover `iref-append` attribute on that same link — cleanup for cards generated by a pre-2.23.2 version of this tool, which wrote that wrong attribute name.

It reuses `#blog-content-id` directly (the same Configure-tab field `generateHTML()` reads) rather than duplicating it as separate Article tab state — that field is already documented as "specific to whichever article is currently being worked on," which is exactly this case too. If it's blank, the fix errors out rather than writing a half-formed tracking string, same rule `buildDataIref()` follows. A card with no `data-offer-id` also errors out (per "no offer ID → skip, show an error" — there's no legacy ID to resolve without one), directing the user to the Configure tab or a manual edit instead.

The offer's legacy ID comes from `card.legacyId`, which `checkAllExpirations()` now also stashes off the back of its existing `fetchOfferStatus()` call (extended to return `legacyId` alongside `status`/`reason`, since the same API response already contains it — no second request). If a card hasn't been checked yet (`card.legacyId` unset), `applyIrefFix()` calls `fetchOfferStatus()` itself on demand before proceeding, so the fix works standalone without requiring "Check Expirations" as a manual prerequisite step.

The actual write is a targeted string splice, not a full-document reserialization: `locateCardHTMLSpan(index)` re-parses `articleOriginalHTML`, walks `findCardElements()`'s results in order aligning each card's `outerHTML` against the raw string (rather than a bare `indexOf()` on just the target card, which could match the wrong one if two cards happen to share identical markup), and returns the exact character span the target card occupies. `applyIrefFix()` mutates only the specific links `analyzeIrefTags()` flagged (via `setAttribute('data-iref', ...)`, using `irefValue()` — the value-building half of `buildDataIref()`, factored out so both call sites share it), then splices that one card's new `outerHTML` back into `articleOriginalHTML` at the located span. This is deliberately different from `removeAndRegenerate()`'s approach (which reserializes `doc.head.innerHTML + doc.body.innerHTML` wholesale) — that reserialization is fine for a final, explicit "Regenerate" output, but doing it on every small mid-editing fix would reformat the entire article each time, same reasoning Find & Replace's string-splice already follows. If a card's re-serialized `outerHTML` can't be found verbatim in the original string (e.g. the source used unquoted attributes or different entity encoding), `locateCardHTMLSpan()` returns `null` and the fix errors out rather than guessing.

A successful fix calls `refreshArticleCardFields()` (which recomputes `irefMissing`/`irefMismatched`, so the badge/button disappear once a card is fully fixed) and invalidates any prior `regenHTML`, same as Find & Replace.

`fixAllIrefIssues()` is the bulk counterpart — a "🔗 Fix All Iref" button in the article-actions row (alongside Check Expirations/Flag Expired/Move All Expired) that runs the fix for every card with an issue instead of clicking "Fix iref" once per card. It calls `applyIrefFix(i)` itself in a plain sequential `for` loop with `await` — deliberately not in parallel, since each call re-parses and re-splices `articleOriginalHTML` fresh, and concurrent calls would race against each other's edits (the same reasoning `locateCardHTMLSpan()`'s fresh-reparse-per-call approach already relies on). Reusing `applyIrefFix()` directly rather than duplicating its legacy-ID-resolution/splice logic means a bulk run gets the exact same behavior as clicking each card's button by hand, including its own per-card toast/Change Log entry as it goes.

Two things are checked once up front, before the loop starts, rather than per card: a blank `#blog-content-id` (would otherwise make every iteration hit the same wall and show the identical error once per card instead of once total) aborts the whole bulk run immediately with one error toast; cards with no `data-offer-id` are filtered out of the loop entirely (same reason — `applyIrefFix()` would just error on each individually) and counted separately in the final summary toast instead. Since `applyIrefFix()` doesn't return anything, success per card is detected by re-checking `card.irefMissing`/`irefMismatched` immediately after each `await` — `refreshArticleCardFields()` inside a successful `applyIrefFix()` call already recomputed them, so an empty result there means that card is now clean.

### Find & Replace (Article tab)

Find & Replace is a two-step preview-then-apply flow, not a single-click blind replace — `previewArticleFindMatches()` ("Find Matches") scans `articleOriginalHTML` for every literal, case-insensitive-by-default match and lists each one with ~40 characters of raw HTML on either side (`findMatchSnippetHTML()`, `FIND_CONTEXT_RADIUS`), stored as `findMatches` (`[{start, end, text, selected}]`, all `selected: true` initially). Nothing is written back to `articleOriginalHTML` at this stage. The reason for splitting it this way: the stated use case is swapping a month/year in a header, but the same literal text often also appears incidentally in body copy, and a blind "replace all" couldn't distinguish the two. Showing raw-HTML context around each match (rather than teaching this code what a "header" is) lets a human see the surrounding tags — e.g. an `<h2>` vs. a plain `<p>` — and uncheck the ones that shouldn't change, without this feature needing any real DOM-structure awareness.

Each match gets its own checkbox (`.find-match-checkbox`, delegated on `#find-matches-list`); `#find-matches-select-all`/`#find-matches-select-none` bulk-toggle all of them, and `#find-matches-counter` always reads "N of M selected". `escapeRegExp()` exists solely so the Find field is matched literally (a user searching for `$5 off` or `20% off` shouldn't get a regex error or a wrong match); the case-sensitivity checkbox is the only actual regex behavior exposed.

`applySelectedFindReplacements()` ("Apply to Selected") does the actual write, and only for matches still checked. It rebuilds the string in a single pass over `findMatches` in order — copying the original text up to each match, then either the replacement or the original matched text depending on `selected`, then advancing past it — rather than calling `.replace()` per match. That one-pass rebuild is deliberate: replacing matches one at a time via repeated string replacement would shift the character offsets of every match still to come, since `findMatches` positions were all computed against the original, unmodified string.

Editing `articleOriginalHTML` directly, rather than re-running `parseAndDisplayCards()` on the result, is deliberate: a full re-parse would rebuild `articleCards` from scratch and lose every flag/status/reorder already applied. Instead `refreshArticleCardFields()` re-derives only the *display* fields (title, callout, CTA text, image, etc. — the same fields `parseAndDisplayCards()` extracts) for each existing `articleCards` entry via `card.index`, leaving `flagged`/`status`/`reason`/array order untouched. This mirrors `toggleArticlePreview`'s "keep list state, refresh display" philosophy, just via `card.index` instead of position.

Because this is a blind text substitution with no awareness of `.bu-card` boundaries, a replace that spans a card's opening/closing tags can change how many cards `findCardElements()` finds — `applySelectedFindReplacements()` compares the card count before and after and appends a warning to the tally line if it changed, rather than silently leaving `articleCards` mapped to the wrong elements. It doesn't attempt to auto-correct this; the user is expected to check flags/order before regenerating.

`findMatches` is invalidated (`clearFindMatchesPreview()`) after a successful apply, on a fresh article parse, and whenever the Find field or case-sensitivity checkbox changes — in all three cases the stored offsets/text no longer correspond to what's currently in `articleOriginalHTML` or to what the Find field currently says, so the list is cleared rather than left showing something that no longer matches reality. Pressing Enter in either the Find or Replace field re-runs the preview rather than applying directly, for the same reason "Replace All" was replaced with a review step in the first place.

Any prior `regenHTML` is invalidated (cleared, and `regen-out-block` hidden) after a successful apply, same as a fresh parse — the previously "final" output no longer reflects the article's current text, and showing it anyway would risk being copied stale. The tracking-link banner is also re-checked against the edited HTML, since a replace could introduce or remove a tracking URL just as easily as a paste can.

### Reordering loaded cards (Article tab)

After "Load from Page", the found-cards list supports drag-and-drop and a per-row position input (`moveArticleCard`, `initArticleDrag`) — same pattern as the Configure tab's offers table, but simpler since there's no lock concept here. `card.index` is set once at parse time in `parseAndDisplayCards()` and never changes afterward — it's the card's position in the *original* DOM (`cardEls` from the source HTML), used only to map back to the right element. Reordering splices the `articleCards` array itself, so array order (display order) and `card.index` (origin) diverge on purpose once a user reorders.

`removeAndRegenerate()` detects a reorder via `articleCards.some((c, i) => c.index !== i)` and, when detected, re-places surviving `.bu-card` elements within their *original* container (not necessarily a single shared one — see below) in the article tab's current array order, slot-based: placeholders mark each card's current position, cards are detached, then dropped back into those positions in the new order (an earlier `appendChild`-to-the-end approach stranded non-card content at the top as blank space — fixed in `2.25.4`). This only runs when `reordered` is actually `true` **and** the article's `#custom-offers-list` count and structure pass `canReorder` — `canReorder` alone is not enough, see below. `canReorder`/the container list are computed *before* removing flagged elements, since a removed element's `parentNode` goes `null` and would fail the check if done after. If reordering is skipped, removal still runs against the full combined card set from `findCardElements()`; the toast says so explicitly rather than silently ignoring the reorder.

Reordering applies **per-container**, not just to a single shared container: `canReorder` requires exactly 1 or exactly 2 `#custom-offers-list` containers (the same active+Expired convention the Expired-group feature below already assumes) with every card a direct child of one of them (`cardEls.every(el => containers.includes(el.parentNode))`) — anything else (0, or 3+), reordering is skipped, same fallback as always. `parentByCardIndex` (a `Map` from `card.index` to that card's original `parentNode`, captured up front before any mutation) is what the reorder-append loop uses instead of one hardcoded container: each surviving, non-moved card is re-appended to *its own* original container, so a card only reorders relative to other cards that already shared its container — active cards resequence among themselves, Expired-section cards resequence among themselves, and a plain reorder never hops a card between the two (that's what `card.moveToExpiredGroup`/the Expired-group move button is for, a deliberate separate action). This is what actually fixed the real complaint that motivated it: an article with an existing Expired section previously couldn't have its active list reordered at all, since `canReorder` used to require exactly 1 container total.

The `reordered` check on the append step (not just `canReorder`) matters because `appendChild` moves every surviving card to the *end* of the container one at a time — running that when nothing was actually reordered has no upside (a plain `.remove()` already closes the visual gap on its own; the flex/grid layout reflows the remaining cards with no help needed) and a real downside: any non-`.bu-card` content sitting inside `#custom-offers-list` — stray whitespace, or a malformed card that's missing its own `.bu-card` wrapper entirely — never gets moved by this loop, since it was never in `cardEls` to begin with. Once every recognized card has been hoisted past it to the end, that stray content is left stranded wherever it happened to originally sit, typically near the top of the list, instead of the plain gap you'd expect where a removed card used to be. This was a real bug (fixed by adding the `reordered` gate) — the loop used to run on every regenerate that had anything to remove, regardless of whether the user had actually dragged/renumbered a card.

### Regenerating with no removal or reorder

`removeAndRegenerate()`'s "nothing to do" no-op used to gate purely on `toRemove.size === 0 && !reordered` — a reasonable check when the only ways to change `articleOriginalHTML` were removing or reordering cards. That stopped being true once Find & Replace (`applySelectedFindReplacements()`) and the iref fix (`applyIrefFix()`) could edit the article's HTML directly without flagging or moving a single card: hitting Regenerate after either would trip the no-op and silently produce no output, even though the loaded HTML had genuinely changed and needed to reach the copyable output block.

`articleHTMLModified` (state, reset to `false` on every fresh `parseAndDisplayCards()`) tracks this: both `applySelectedFindReplacements()` and `applyIrefFix()` set it to `true` on a successful edit, and the no-op gate now also checks `!articleHTMLModified` before bailing out. It isn't reset after a successful regenerate — same as `flagged`/reorder state, which also aren't reset — since the gate's job is "has anything changed since the *original* load," not "since the last regenerate." When a regenerate happens purely off this flag (no cards removed, moved to the Expired group, or reordered), the toast/Change Log say "applied edits (Find & Replace / iref fix)" rather than showing an empty reason. The gate also checks `toMoveToExpired.size === 0` for the same reason — see "Expired group" below, a card marked to move is itself a genuine reason to regenerate even with nothing removed or reordered.

### Expired group (Article tab)

Some articles (this feature was built directly off one, a real DealNews Uber piece with "Uber Eats July/June/May/April 2026 Promo Code" cards each carrying an "Expired Promo" CTA) intentionally keep expired cards on the page instead of deleting them, consolidated into their own section — a heading (e.g. "Expired Uber Promo Codes") followed by a second `#custom-offers-list` container, separate from the main active-offers one. Before this feature, moving a newly-expired card into that section meant cutting its markup out of the active list, rewriting its CTA text by hand, and pasting it into the expired section directly in the CMS. This automates that specific move.

`card.moveToExpiredGroup` is a new per-card boolean, mutually exclusive with `card.flagged` — `toggleFlag()`/`toggleMoveToExpiredGroup()` each clear the other when turning itself on, since a card is either removed or relocated on regenerate, never both. `toggleMoveToExpiredGroup(i)` is the per-card "🗄️" button (next to 🚩 in both the list row and the visual preview's CTA row); `moveAllExpiredToGroup()` is the bulk button ("🗄️ Move All Expired," next to Flag Expired/Flag All Except Kept/Unflag All). Unlike `flagExpired()`/`flagAllExceptKept()`, the bulk version does **not** skip `keepDespiteExpired` cards — a card an editor already chose to keep despite being expired (CTA text already says so) is exactly the kind of card this feature exists to consolidate into the group, not something to leave where it is. Both the per-card badge (`badge-move-expired`, "→ Expired Group") and the status bar tally sit at the same priority level as `flagged`/`keepDespiteExpired` in `badgeClassForStatus()`/`badgeLabelForStatus()`/`badgeTitleForCard()`/`updateArticleStatusBar()`.

`removeAndRegenerate()` computes `toMoveToExpired` the same way it computes `toRemove` — a `Set` of `card.index` values, built with a `!toRemove.has()` guard that's redundant given the mutual exclusion above but costs nothing as a safety net. Before any DOM mutation, if `toMoveToExpired.size > 0` it requires `containers.length === 2` exactly (the same `containers` array already computed for the `canReorder` check) — the *later* one in document order (`containers[1]`) is assumed to be the existing Expired section, since that matches every real example seen so far (heading + second list, appearing after the active list). If the article doesn't have exactly 2 `#custom-offers-list` containers, the entire regenerate is refused with an error toast rather than run partially or fabricate a heading — there's no article-agnostic way to guess appropriate heading text (a brand name is usually baked into it, e.g. "Expired *Uber* Promo Codes"), so this deliberately requires the section to already exist, rather than auto-creating one with generic text the editor would just have to rewrite anyway.

The move itself: `PROC_TARGET_CLASS` (`.btn-cta`) selector finds the CTA element inside the card exactly like `flagExpired()`'s CTA-text detection does, its `textContent` is rewritten to `EXPIRED_GROUP_CTA_TEXT` ("Expired Promo"), then `expiredContainer.insertBefore(el, anchor)` relocates the whole card element — landing at the *top* of the existing Expired section, ahead of whatever's already there, consolidating rather than replacing. `anchor` is `expiredContainer.firstChild`, captured once before the move loop starts (not re-read per card — re-reading it each iteration would mean every newly-inserted card becomes the next anchor, reversing the moved cards' order relative to each other); inserting every moved card before that same fixed anchor puts them all above the pre-existing section content while preserving their own relative order from `articleCards`. This runs in `articleCards` array order (matching how the reorder-append loop above it orders things), and is applied *after* removal but *interleaved with* the reorder step's own exclusion: the reorder loop explicitly skips any card in `toMoveToExpired` (`!toMoveToExpired.has(c.index)`) so it never tries to re-append a moving card back into the *primary* container, fighting the `insertBefore` into `expiredContainer` over where the card ends up.

A moved card's own `card.moveToExpiredGroup`/`ctaText` fields in `articleCards` are **not** updated after a successful regenerate — same as removed cards' `flagged`/`status` fields, which also aren't cleared. `regenHTML` is a separate output snapshot; the tool's own state reflects the *pre-regenerate* intent, so clicking Regenerate again without reloading reapplies the same move against the same original `articleOriginalHTML`, producing identical output (idempotent, same as re-removing an already-removed card would be).

Because `EXPIRED_GROUP_CTA_TEXT` contains "expired," a card moved this way and later re-pasted into a fresh "Load from Page" will be detected as `keepDespiteExpired` automatically on the next parse — no special-casing needed to keep that in sync with the "Intentionally-expired cards" behavior described below.

### Blog Slider (removed)

An earlier "Slider" tab generated the `<div class="blog-slider" title="…" link="…" category="…" facets="…" store="…" iref-append="1">` component — a separate front-end widget (not part of this extension) that self-populates a horizontal deal carousel on the live site from whichever of `category`/`facets`/`store` are present. It was removed in `2.9.1`: it was built as a jumping-off point toward getting *vertical* deal cards for a category/facet/store, but `blog-slider` always renders as a horizontal carousel — that's fixed by the live site's own front-end code and can't be changed from this extension. The Auto Cards tab was the feature that actually replaced it — but that tab has since been removed too (see version history), so this extension currently has no tool for category/facet/store-driven card generation at all. `blog-slider` itself still exists and still works as a live-carousel widget on the public site; this extension just no longer has a tool for generating that specific div.

### Live Feed Generator (`index.html`) — removed from the extension in `2.20.1`

The Live Feed generator used to be a tab in this extension (`sidebar.js`'s `generateLiveFeedHTML()`) with `index.html` at the repo root as a manual, verbatim port for anyone without the extension installed. In `2.20.1` the tab was removed from the extension entirely — `generateLiveFeedHTML()`, `fetchDealNewsOffers()`, `buildStaticSnapshotHTML()`, `renderLiveFeedOut()`, `copyLiveFeedHTML()`, the `pane-live`/`tab-live` markup, and the now-unneeded `https://api.dealnews.com/*` `host_permissions` entry were all deleted from `sidebar.js`/`sidebar.html`/`manifest.json` — so `index.html` is now the *only* place this tool exists, not a port of anything. All of the reasoning below still applies to `index.html`'s own copy of these functions; there's no other copy left to drift out of sync with.

A single self-contained HTML file at the repo root, entirely separate from the extension — not referenced by `manifest.json`, not loaded by anything else here. Same form fields, same hybrid static-snapshot-plus-live-refresh output described below.

Unlike a normal static-HTML generator, this tool's output is a `<div>+<script>` pair — `generateLiveFeedHTML()` produces a snippet that fetches directly from `https://api.dealnews.com/content` (query params `category_id`/`facet_ids`/`vendor_id`) and renders vertical `.bu-card` markup client-side. Because the refresh fetch happens in the visitor's browser rather than only at generation time, the deals shown stay current indefinitely, without re-pasting anything.

`generateLiveFeedHTML()` is hybrid, not purely live: it also fetches the same `api.dealnews.com` data **once at generation time** (from this page itself, subject to normal browser CORS — see below) and bakes that result into the output as a real, static `.bu-card` snapshot (`buildStaticSnapshotHTML()`), sitting in the article's raw HTML *before* the `<script>` tag. This exists for SEO: search crawlers that don't execute JavaScript (or render it on a significant delay, which is most of them) see actual offer content immediately in the page source, not an empty shell waiting on a client-side fetch — the same problem a purely-live widget has no way around. The live-refresh `<script>` then replaces that static snapshot with fresh results for real visitors once the page loads (see below) — crawlers get the snapshot, humans get the live version, and if the live refresh fails or returns nothing, the snapshot just stays put rather than the widget going blank. The tradeoff versus a purely-live version: the snapshot is a point-in-time capture, only as fresh as whenever the snippet was last generated, and the output is larger (it now carries both the static payload and the refresh script) — but it's never *empty* for a crawler, which a purely-live widget always was.

If the generation-time fetch itself fails (network issue, a bad Category/Facet/Store value, the API being briefly down), `generateLiveFeedHTML()` doesn't fail the whole generation — it catches the error, falls back to an empty snapshot, and returns `snapshotFailed: true` alongside the still-valid live-refresh-only output, surfaced as a non-fatal warning rather than blocking Generate, since a live-refresh-only widget is still a usable result.

`api.dealnews.com` is DealNews's own public content API — the same one `blog-slider` itself calls, discovered by inspecting `blog-slider`'s actual network request on a live article (`window.DealNews.els` in the page's own JS exposed the exact config shape: `apiKey`/`category_id`/`facet_ids`/`vendor_id`/`count`/`refcode_append`). The request needs an `Authorization: DN <apiKey>` header — a custom scheme, not a standard Bearer token — which isn't visible in the Request URL at all; an early version of this snippet omitted it entirely (since the URL alone gave no indication a header was required) and got a `400 Missing Authorization header` in response, only found by loading the failing request's URL directly in a browser tab to read the JSON error body DevTools itself couldn't display, then diffing against `blog-slider`'s own Request Headers on a working page. The same literal key (`jxqfz29pbv9xpWSYnmJX`) was observed on every `blog-slider` instance checked regardless of its category/facet/vendor config, so it's a shared, site-wide public key meant for exactly this kind of client-side use — hardcoded directly into the generated script rather than exposed as a form field, the same way `blog-slider` itself bakes it in rather than varying it per instance. Likewise the exact response shape (`content` array of offer objects with `headline`/`call_out`/`value_statement`/`images`/`vendor`/`offsite_url`) was captured from that same live response — a good starting contract, but not a guarantee DealNews won't change it.

Before building this, two things were verified live rather than assumed: (1) whether a `<script>` tag pasted into an article body actually executes — confirmed yes, but **only on the published page**, not in the CMS's own preview, which apparently doesn't run any page scripts at all (an initial test read as a false negative until it was noticed `blog-slider` itself — a working, pre-existing feature — also never renders in preview for the same reason); (2) the request/response shape itself, pulled from DevTools on a live article rather than guessed.

`generateLiveFeedHTML()`'s inner script builds every card via DOM APIs (`createElement`, `.textContent`, `.href`, `makeLink()`) rather than concatenating HTML-tag strings. A first version built cards with strings like `'<img src="' + imgUrl + '">'`, and DealNews's save/publish pipeline turned out to regex-scan raw article HTML for `<img src="...">`-shaped patterns (likely an image-preload or featured-image detector) without knowing to skip over `<script>` tag contents — it found that literal fragment sitting inside the script's JS source, misread it as a real tag, and mangled the saved script badly enough that nothing executed at all (confirmed live: the misidentified "src" showed up as an actual 404 request for the literal text `' + imgUrl + '`, and the console showed no fetch to `api.dealnews.com` ever fired). Building nodes via the DOM instead means no `<tag` text ever appears in the saved script source for that scanner to misinterpret. This is also *why* the very first viability test (a `<script>` setting `innerHTML` to a literal `'<strong>SCRIPT EXECUTED</strong>'` string) was a false positive for "scripts execute": that string was a complete, well-formed HTML fragment on its own, so the same regex-based mangling could have statically extracted and rendered it as markup — identical to genuine execution — without the JS ever actually running. The real confirmation came from a payload with no `<tag`-shaped text anywhere in it (`textContent = 'REAL JS RAN: ' + (2+2) + ' at ' + new Date().toISOString()`), which could only produce its result via live computation.

Building via DOM APIs also makes manual HTML-escaping of live API fields unnecessary — `.textContent`/`.href`/`.title` assignment is inherently safe — so there's no separate runtime `esc()` the way the string-concatenation version needed. The `cfg` object (category/facet/vendor/count/ctaText) is still embedded into the script via one `JSON.stringify(cfg)` call, safely handling any character — including a stray apostrophe in CTA text — as valid JS source. `title`/`link` (the optional heading) go through this page's own `esc()` instead, since those become static HTML immediately, outside the `<script>` block, and were never implicated in the `<img>`-scanning bug.

Every widget instance gets a random `uid` (`dn-live-` + a short random string) as its container `id`, so multiple Live Feed widgets can coexist on one page without colliding — the generated script only ever queries its own container by that id. If the live refresh fetch fails or returns zero matching offers, the script does nothing (`return` inside the `.then()`, an empty `.catch()`) rather than hiding the container — the static snapshot baked in at generation time is already there and stays visible; there's no "blank" state to fall back to the way the purely-live version needed. When the refresh does succeed, it looks for an existing `.bu-vertical-offers` element and calls `.replaceWith()` on it (falling back to `appendChild` if none exists, e.g. if the snapshot was empty) — swapping in fresh cards rather than stacking a second copy alongside the snapshot.

The API's `images` object carries several pre-sized URLs (`Small` 45px up through `Maximum` 900px+), and the card's image box is 200x200px — the widget picks the first available size at or above that (`XL` → `XXL` → `Maximum` → `Large` → `Medium`) rather than the first one that merely exists, since defaulting to a smaller size (e.g. `Medium` at 75px) means the `<img>` gets upscaled to fill the box and looks visibly blurry.

This page has no `host_permissions` superpower — it's a plain webpage, not an extension — so its generation-time snapshot fetch is subject to normal browser CORS for whatever origin it's hosted on (a `file://` path, GitHub Pages, wherever). In practice this was tested from a `file://` origin and worked — `api.dealnews.com` appears to accept it — but `generateLiveFeedHTML()` still wraps that fetch in a try/catch and falls back to a live-refresh-only snippet (`snapshotFailed: true`) rather than failing Generate outright, in case some hosting origin is ever rejected.

## Known editor environment (secure.dealnews.com article edit pages)

- No TinyMCE, no CKEditor, no CodeMirror on the main window
- Article body lives in `textarea#normal-body-editor`, but that textarea is just a mirror — the real editing surface is a same-origin `iframe` (`src="javascript:false"`, `contentDocument.designMode === "on"`) that a legacy WYSIWYG library injects next to it. The container wrapping both textarea and iframe uses the id convention `<field>` (e.g. `normal-body` wraps `normal-body-editor`, `teaser-body` wraps `teaser-body-editor`).
- `window.YAHOO` is not present, so this isn't YUI2's Editor despite matching its `javascript:false` iframe signature — likely an in-house or vendored fork.
- The iframe sanitizes complex nested markup both on load and on sync-back (see "No Save to Page" and the editor-detection note above) — treat this field as read-*and*-write-unreliable for anything beyond the textarea's raw value.
